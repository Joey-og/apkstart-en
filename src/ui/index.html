Install Android to the virtual disk

The virtual machine window is open. Follow the 6 steps below once, and after that ApkStart will boot straight from disk and will no longer need the image.

  1. Boot menu: use ↓ to select Installation - Install Android-x86 to harddisk, then press Enter
  2. Choose Partition: select Create/Modify partitions; when asked whether to use GPT, select No
  3. cfdisk partitioning：New → Primary → press Enter to accept the size → Bootable → Write → type yes → Quit
  4. Format: select vda1 -> when prompted to format, select ext4 → Yes
  5. Bootloader and system：Install GRUB select Yes；Install /system as read-write select Yes
  6. Done: when progress reaches 100%, click "I have finished installing" below (ApkStart will restart and take over automatically)

If you later see a message that adb is not connected: in the VM window press Ctrl+Alt+F1 to open a terminal and run setprop service.adb.tcp.port 5555、stop adbd、start adbd， Then press Ctrl+Alt+F7 to return to the graphical interface.

Automatic mode (default, nothing to configure)
Detecting...
Memory, core count, rendering backend, port, and acceleration method are all chosen automatically. If startup fails, it retries automatically with reduced settings, so you do not need to change anything by hand. ApkStart uses its own adb server port 5044 (your own system adb uses 5037), so on the command line adb devices will not show this Android device. That isolation is intentional. To connect, use $env:ANDROID_ADB_SERVER_PORT=5044 and then run adb. Note: do not manually run adb connectagainst port 5555. That will pop up a system dialog asking "Allow USB debugging?" over the running app.
Calculating...
One system image is shared by the whole machine, and app data is stored in a differencing layer. Old images, old snapshots, logs, and lock files can all be reclaimed. Logs roll over automatically past a limit and will not grow forever. "Reset Android data" really deletes several GB of user data and keeps only the system itself.
The diagnostics report helps with troubleshooting. Rebuilding restores the desktop and Start menu entries.
Stays in the tray after you sign in to Windows, so double-clicking a desktop icon opens apps instantly with no manual startup.
App window
Press F11 at any time or use the tray menu to switch. Fullscreen only enlarges the window and does not change the picture aspect ratio, and switching does not restart the app.
When on, opening an app fills the screen right away, with no need to press F11. It works best together with "Landscape" below , because the landscape panel aspect ratio already matches the screen, so fullscreen leaves no black bars.
Android portrait/landscape is decided by the real orientation of the virtual phone panel. When the panel orientation does not match the orientation the app itself declares, Android only gives the app a narrow strip in the middle with black bars on both sides, and resizing the window or changing the resolution cannot fill it. "Follow the app" reads the app orientation when the APK is installed and automatically switches the panel to match at launch, so apps like Hongguo and Modu appear upright and fill the screen. The runtime restarts once only when the orientation is wrong (about ten seconds or so), and after that, apps with the same orientation open instantly.
In Android, the auto-rotate switch is on by default. Note that this does not affect the picture orientation: panel orientation and screen orientation are still decided by the policy above plus ignoring app orientation requests, and will not be thrown off by the sensor. It only matters for the few apps that read this switch value.
A width of 720 at 190dpi works out to 606dp, which just crosses the Android 600dp tablet breakpoint, so the two-column episode pages in Hongguo and split-pane settings pages only appear in this layout. Turning it off returns to the phone layout (larger text, less information). Takes effect the next time you open an app after switching.
This is the physical panel orientation the runtime is using right now, written automatically by the policy above. Only in a "Force" mode is it entirely up to you.
A native window is rendered and laid out directly by the emulator. Dragging, scaling, and rotating feel responsive, with no black bars or misaligned clicks. The cost is an extra taskbar icon (in landscape, use the tray menu or Ctrl+Alt+R). Embedded mode puts the emulator window inside our window, which looks more unified and has its own rotate button, but tends to drop frames and show black bars when scaling, rotating, or switching apps. Changes take effect the next time you open an app.
In window mode you can drag the borders to resize freely. This sets the internal Android rendering size: smaller is lighter on performance.
Mouse buttons
The emulator treats the left button as a finger tap natively. Press and drag to swipe. No extra setup needed.
By default the emulator also treats the right button as a tap (easy to trigger by accident). When this is on, the right button only performs Back and no longer triggers a tap.
Smooth mode merges scrolling over a short period into a single swipe gesture, avoiding notch-by-notch judder and avoiding starting an adb process for every notch.
Side button mapping needs a global mouse hook. The hook is installed only while an ApkStart app window is in the foreground and is removed immediately on losing focus or closing, so it will not slow down the desktop.
The mappings above apply only while an app window is in the foreground. After switching back to the desktop or closing the window, mouse behavior returns fully to native Windows behavior.
Key mapping (game controls)
Map keyboard keys to Android touchscreen taps and swipes. Good for playing mobile games with a keyboard (WASD to move, J/K for skills, and so on). Each app can be configured separately. Right-click an app card and use "Key mapping" to pick a preset template or customize.
The current app has no key mapping configured. Right-click an app card to quickly apply a preset template.
Performance and resource usage
Decides how much CPU the Android VM uses and how detailed the picture is. If Hongguo or Douyin stutters, switch to "Smooth". If you just want small apps idling in the background, switch to "Save resources". Takes effect the next time you open an app.
Expansion is done in place: installed apps and save data are kept. The next app launch just takes about ten seconds longer.

Container details (advanced)
Tightens the vCPU quota and lowers the process priority so the CPU yields to the Windows desktop first. The "Resource policy" above already sets this automatically.
Game mode keeps the Android VM at a higher CPU priority and reduces host-side polling, giving the lowest input and picture latency. The cost is that other programs on the machine slow down. When no app window is open, the container still lowers its priority and parks automatically.
Additionally disables background packages such as the Play Store, setup wizard, and print services, keeping only what is needed to open apps. If an app complains that Google Play services are missing, turning this switch off restores them automatically.
After ApkStart starts, it boots the Android environment in the background (the window stays hidden the whole time, so you never see the emulator). After that, opening any app is a single click, measured as dropping from over 20 seconds to almost no wait. The cost is about 1 GB of memory kept resident while idle. If you turn it off, the first app launch needs a cold start.
The Android environment boots once and stays resident. Later app launches do not rerun the whole system; they only start that app and stop other app processes. Closing the last window clears the background and parks the container, and the next launch is still instant.
Download and update sources
"Automatic" asks both GitHub and Gitee for the latest version, actually downloads 256 KB from each download address to test its speed, and then downloads from the fastest one. If one source is unreachable, updates still work.
When a direct GitHub connection is too slow, it also speed-tests ghfast.top and gh-proxy.com, two public forwarding services (they only forward public release files and involve no accounts). Turn this off to use only direct connections and any prefix you enter yourself.
If filled in, only your prefix is used and the two public mirrors above are not tried. Leave it empty to let the "Automatic" logic decide. The downloader prepends it to the real address.
Large files are downloaded in parallel chunks. The default of 8 threads already saturates most home broadband. On a stable network you can try 16.
Gitee update source (optional)
This project repo is public, so the Gitee release list can be read anonymously and the Gitee source works with this left empty. You only need to fill this in if Gitee rate-limits you (returns 403/429) or you want to read a private branch: gitee.com, then Settings, then Personal tokens. Check only "projects". It is used only to read the release list and does not upload anything.
PC health check and auto configuration
First it checks this machine: whether CPU virtualization is on, whether the Windows hypervisor platform is present, what the graphics card is, how much video memory it has, and whether memory and the system version are enough. Anything that can be changed automatically (memory / cores / picture quality / rendering backend) is written straight into the settings, and the result is saved as a driver. Items needing administrator rights get a button, and items that can only be changed in the BIOS come with instructions.
Drivers and compatibility patches
Some machines only run after changing launch parameters (old graphics cards with a low GLES version, hardware acceleration off, or a driver version that crashes as soon as hardware rendering is enabled). A driver is a JSON file: it declares which machines it matches and which launch parameters to change on a match. You can write, import, and share them yourself. Drivers only change allowlisted launch items and do not run any code. If a driver does not match, it has no effect.
Reading drivers...
"Export a template for this PC" fills in the match conditions for this machine. Edit gpuMode / forceTcg and it is ready to use. See field descriptions in docs/drivers.md in the repo.
Automatic checks and smart diagnostics
Periodically checks this machine in the background: whether the Android runtime is up, whether adb authorization is normal, how much disk is left, whether the data partition is blocked by a differencing disk, whether the snapshot is broken, and whether any settings conflict with each other. It only pops up a notification once when it finds a new serious problem. Everything else is listed quietly below.
When off, there are no more scheduled scans. You can click "Run check now" at any time to run one manually.
Notifications only pop up for serious problems. Known old problems do not bother you again.
